# Phase F.2.8.3 Slice 3.7 Discovery: Durable Outbox Reconciliation & Recovery

## 1. Source of Truth Terminology
The architecture strictly enforces the following roles:
- **PostgreSQL durable source records** (e.g., `tickets`, `escalation_events`) are **authoritative**.
- **`LogicalNotificationIdentity`** acts purely as a deterministic notification identity and deduplication contract.
- **`outbox_events`** represents the **durable notification intent**.

## 2. Durable Reconstruction Matrix
Reconstruction depends entirely on the availability of an authoritative source record. 

| Notification Type | a. Authoritative Source | b. Source Identity | c. Data Required for Payload | d. Recipient Principal | e. Recipient Delivery Address | f. Logical Identity Derivation |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **ESCALATION_TEAM** (E1) | `escalation_events` (type=support) | `escalation_event_id` | Event context, session metadata | `team:support` | Configured support channel email | `(source_event_id, ESCALATION_TEAM, team:support)` |
| **ESCALATION_CUSTOMER** (E2) | `escalation_events` (type=customer) | `escalation_event_id` | Event context, session metadata | `customer:{id}` | `customers.email` via join | `(source_event_id, ESCALATION_CUSTOMER, customer:{id})` |
| **TICKET_CREATED** | `tickets` | `ticket_id` | Ticket ID, subject, metadata | `customer:{id}` | `customers.email` via join | `(ticket:{ticket_id}, TICKET_CREATED, customer:{id})` |
| **TICKET_RESOLVED** | `tickets` | `ticket_id` | Ticket ID, resolution notes | `customer:{id}` | `customers.email` via join | `(ticket:{ticket_id}, TICKET_RESOLVED, customer:{id})` |
| **CUSTOM_EMAIL** | *Limited* (`idempotency_records`) | `client_request_id` | **Missing** (LLM generated body) | `customer:{id}` | `customers.email` via join | `(customer:{id}\|req:{req_id}, CUSTOM_EMAIL, customer:{id})` |

**CRITICAL LIMITATION - CUSTOM_EMAIL:**
If a `CUSTOM_EMAIL` outbox row is entirely missing, it **cannot** be automatically reconstructed. While the `idempotency_records` table captures the *intent* execution for a specific `client_request_id`, the actual text (subject/body) generated by the LLM is only stored in the outbox payload. Because this text does not exist durably outside the outbox, automatic repair is impossible. To reconstruct custom emails, the exact LLM payload would need to be stored in an authoritative domain table.

## 3. Outbox State Reconciliation
Reconciliation rules ensure zero duplicate intents and respect existing worker semantics:
- **Missing:** Safely enqueue the notification using `INSERT ... ON CONFLICT (logical_identity_hash) DO NOTHING`.
- **SENT:** Never recreate automatically. The durable intent was fulfilled.
- **PROCESSING (fresh lease):** Ignore entirely. Leave the worker-owned row alone.
- **PROCESSING (stale lease):** Ignore entirely. The existing `RECOVER_STALE_SQL` lease-recovery sweep natively handles this.
- **RETRYABLE:** Ignore entirely. The worker owns the retry lifecycle.
- **FAILED (terminal):** Do NOT blindly recreate. Terminal failures require an explicit manual recovery or operator intervention path, as they indicate a permanent external rejection (e.g., hard bounce).

We explicitly reuse the existing worker state machine. No secondary lease mechanism will be created.

## 4. Reconciliation Concurrency
The `logical_identity_hash` uniqueness invariant guarantees at most one durable notification intent per logical identity. Both "checking for missing" and "enqueueing" are race-safe.
- **Two Reconcilers concurrently:** Safe. `ON CONFLICT DO NOTHING` ensures only one successfully inserts the `PENDING` row.
- **Reconciler + Worker:** Safe. The reconciler ignores existing rows, while the worker actively updates them.
- **Reconciler + Stale-Lease Recovery:** Safe. These are disjoint operational domains (reconciler inserts new rows, recovery updates existing `PROCESSING` rows).

## 5. Reconciliation Triggers
The chosen trigger model employs a combination of execution contexts:
1. **Startup Reconciliation:** 
   - *Purpose:* Catch up on intents missed during deployment windows, extended API downtime, or catastrophic process failure.
   - *Frequency:* Once per application startup.
   - *Ownership:* Main application lifecycle / startup hook.
   - *Requirement:* Best-effort catch-up.
2. **Periodic Reconciliation:**
   - *Purpose:* Repair systemic gaps continuously (e.g. database disconnects right before outbox insertion).
   - *Frequency:* Infrequent (e.g., hourly cron).
   - *Ownership:* Dedicated background daemon task or external cron trigger.
   - *Requirement:* Required for strict eventual consistency.
3. **Manual / Admin Reconciliation:**
   - *Purpose:* Targeted repairs for specific tickets, escalations, or historical data recovery.
   - *Frequency:* On-demand via operator action.
   - *Ownership:* Admin API endpoint / CLI tool.
   - *Requirement:* Operator-driven tool.

## 6. Retention / Reconstruction Horizon
A notification is only "repairable" as long as its authoritative source record exists.
- Authoritative source data MUST remain available for at least the entire reconciliation/reconstruction horizon.
- For every notification type: source record retention >= maximum period during which a missing notification may be repaired.
- If the durable source is deleted before reconciliation runs, reconstruction is impossible.
- Outbox retention alone cannot compensate for missing source data.
- `CUSTOM_EMAIL` remains non-reconstructible while subject/body exist only in the outbox. Do not claim automatic reconstruction for `CUSTOM_EMAIL` unless a durable source containing all required content exists.

## 7. Failure Semantics
- **Source event committed, outbox missing:** The reconciler detects the missing `LogicalNotificationIdentity` and inserts the `PENDING` outbox row exactly once.
- **Outbox committed, worker crash:** The worker restarts, leaving previous rows in `PROCESSING`. The lease naturally goes stale and the existing recovery sweep transitions them to `RETRYABLE`.
- **SMTP provider accepts message but worker times out:** The worker crashes or network drops before marking the row `SENT`. The row goes stale, is recovered to `RETRYABLE`, and sent again. *(At-least-once external delivery).*
- **Stale PROCESSING recovered while old worker is still running:** The old worker eventually tries to mark the row `SENT`, but its `claim_token` is rejected by the database since the recovery sweep cleared it. The old worker fails gracefully without corrupting state.
- **Reconciliation runs concurrently with a successful worker send:** The reconciler attempts an insert which is ignored via `ON CONFLICT DO NOTHING` due to the `SENT` row's `logical_identity_hash`.

**Invariant:** Durable intent guarantees exactly-once persistence. External SMTP delivery guarantees at-least-once physical dispatch. We do NOT claim exactly-once physical email delivery.

## 8. E1/E2 and Source Event Identity
- **E1 and E2 are independent escalation events:** Both E1 (e.g. first escalation in session) and E2 (e.g. subsequent escalation) are distinct rows in `escalation_events`.
- **Each escalation event independently requires:**
  - `ESCALATION_TEAM` notification (always required).
  - `ESCALATION_CUSTOMER` notification (required ONLY when `customer_notification_required = true`).
- **Reconciliation Independence:**
  - E1 reconciliation evaluates the unique `escalation_event_id` for E1 and repairs any missing required notifications (team and/or customer).
  - E2 reconciliation evaluates the unique `escalation_event_id` for E2 and independently repairs any missing required notifications (team and/or customer).
- Escalation notifications are NEVER reconstructed purely from a `session_id` or an `ACTIVE` escalation state in memory or Redis.

## 9. Existing Architecture
The reconciliation system **MUST REUSE**:
- `LogicalNotificationIdentity`
- The existing `OutboxWorker`
- The existing `claim_token` locking mechanics
- The existing stale recovery SQL (`RECOVER_STALE_SQL`)
- The existing `RetryPolicy`

The architecture will **NOT CREATE**:
- A second outbox table
- A second identity system
- A second lease system
- A new event framework
- A new worker

## 10. Final Discovery Acceptance Criteria
1. **Reconstruction Source Check:** Ensure every notification type (except `CUSTOM_EMAIL`) successfully maps to an authoritative domain table for reconstruction.
2. **Missing Intent Repair:** Prove that a missing required intent is safely reconstructed into a single `PENDING` outbox row when the authoritative data exists.
3. **Concurrency Uniqueness:** Prove that concurrent reconciliation does not produce duplicate identities (enforced by DB constraints).
4. **SENT Preservation:** Prove that a `SENT` notification is never blindly recreated by a reconciler.
5. **Stale Lease Handling:** Prove that stale `PROCESSING` rows correctly follow existing lease recovery rather than reconciliation logic.
6. **E1/E2 Independence:** Prove that E1 and E2 identities remain distinct and are reconciled solely via `escalation_events`.
7. **Custom Email Limitation:** Explicitly test and document that `CUSTOM_EMAIL` reconstruction is safely skipped or flagged when the LLM payload is unrecoverable.
8. **Isolation:** Prove that a reconciler cannot infer and reconstruct notifications from `session_id` alone.
